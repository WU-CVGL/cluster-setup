# Proxy account applier

`proxy_apply.py` applies proxy account changes requested by the proxy portal: it updates the accounts file (`services/proxy-accounts/accounts.json`), renders and checks the configs, restarts the proxies and verifies the result. It runs on the supplementary services VM as root, started by systemd. The portal only writes request files into a spool folder; it never gets the Docker socket, the accounts file or a shell on the host. Python 3.6 or later, standard library only. How accounts work: [docs/00](../../../docs/00_Network_Proxy.md#accounts).

## Install

The units and the settings file are in [`services/system-configurations/etc`](../../system-configurations/etc): `systemd/system/proxy-apply.service`, `proxy-apply.path`, `proxy-apply.timer` and `default/proxy-apply`.

```sh
cd ~/ws/cluster-setup/services
sudo useradd --system --no-create-home --shell /usr/sbin/nologin proxy-portal   # the portal's uid
sudo install -m 644 system-configurations/etc/systemd/system/proxy-apply.{service,path,timer} /etc/systemd/system/
sudo install -m 644 system-configurations/etc/default/proxy-apply /etc/default/proxy-apply
sudoedit /etc/default/proxy-apply   # PROXY_APPLY_SERVICES_DIR: this checkout's services folder
sudo python3 proxy-portal/applier/proxy_apply.py --requester proxy-portal init   # the spool
sudo systemctl daemon-reload
sudo systemctl enable --now proxy-apply.path proxy-apply.timer
```

The settings come from `/etc/default/proxy-apply` only, never from a request:

| Setting | Default | |
| :--- | :--- | :--- |
| `PROXY_APPLY_SERVICES_DIR` | the folder above this one | the `services/` folder of the checkout |
| `PROXY_APPLY_REQUESTER` | | user name or uid allowed to write requests |
| `PROXY_APPLY_SPOOL` | `/var/lib/proxy-portal/spool` | also fixed in `proxy-apply.path` |
| `PROXY_APPLY_COMPOSE_FILE` | `<services>/docker-compose.yml` | |
| `PROXY_APPLY_COMPOSE_PROJECT` | Compose's default | |
| `PROXY_APPLY_HA_HTTP` | `127.0.0.1:30889` | the HA entry's HTTP port on the host |
| `PROXY_APPLY_PROBE_URL` | `https://www.google.com/generate_204` | fetched through the HA entry to verify |
| `PROXY_APPLY_VERIFY_TIMEOUT` | `60` | seconds |

`proxy-apply.path` starts the service while a request is waiting; `proxy-apply.timer` runs it every 5 minutes to expire results and to recover an interrupted apply. Its log is in `journalctl -u proxy-apply`. Files the applier replaces keep their owner, so the admins' `proxy_accounts.py` keeps working on them.

## Spool

| Path | Owner, mode | Content |
| :--- | :--- | :--- |
| `requests/` | requester, `0700` | requests, one file each |
| `results/` | requester, `0700` | one-time results: a new password, file mode `0400`, owned by the requester |
| `status/` | root, `0755` | one status file per request |
| `status.json` | root, `0644` | the accounts without passwords: `proxy_accounts.py status --json` |

The portal mounts the spool. It writes a request under a name that does not end in `.json` and then renames it to `<id>.json`, so a request is never read half-written. The applier reads every `*.json` entry and removes it, whether valid or not. It opens the entry without following links, and accepts only a regular file with one link, owned by the requester and at most 4096 bytes.

## Requests

```json
{"id": "0f8e1c2a-1111-4222-8333-944455556666", "op": "disable", "username": "alice"}
```

- **`id`**: 8 to 64 characters, lowercase letters, digits and `-` (a UUID), and the file name without `.json`. An id that already has a status file is dropped.
- **`op`**: `add`, `rotate`, `enable`, `disable` or `remove`. Raw auth and rendering stay with `proxy_accounts.py`.
- **`username`**: the account, checked by the same validator as `proxy_accounts.py`. `svc-ha` and `svc-monitor` are refused: they are changed with `proxy_accounts.py` only.
- No other key is accepted. A request carries no password, path or command.

**Passwords** for `add` and `rotate` are generated by the applier, as `proxy_accounts.py` does. The new password is written to `results/<id>.json` (`{"id", "username", "password"}`) once the change is live (`applied` or `unconfirmed`). The file is mode `0400` and owned by the uid that wrote the request. The portal shows it once and deletes it; the applier deletes results older than 10 minutes. So no secret travels from the portal to the host, the requests can be kept as they are, a failed request leaves no password anywhere, and a password exists only for an account that works.

## Statuses

`status/<id>.json` holds `id`, `op`, `username`, `status` and `updated_at`, plus:

| `status` | Meaning |
| :--- | :--- |
| `applying` | in the current batch |
| `applied` | live and verified; `restarted` lists the services restarted, `changed: false` when nothing had to change |
| `failed` | not applied; `stage` and `error` say why. `restored: true`: the previous files and running state are back (or nothing was touched). `restored: false`: the rollback did not finish; check `xray-ha` |
| `unconfirmed` | live, and every login that must be refused is refused, but no line answered the logins that must pass in time (a line or the probe URL may be down). The result file is written |

`stage` is one of `request` (invalid, or the account does not allow the operation; the other requests of the batch go on), `accounts`, `render`, `test`, `precheck`, `backup`, `swap`, `restart`, `verify` or `interrupted`.

## How a batch is applied

The applier holds the accounts lock (`proxy-accounts/.lock`, the one `proxy_accounts.py` takes) for the whole run, and takes up to 64 pending requests at a time, oldest first:

1. Applies the requests to a copy of the accounts in memory; one that cannot apply (e.g. `add` of an existing account) fails alone.
2. Renders every config in memory. Disabled accounts are left out of every inbound.
3. Runs `xray run -test` on each changed Xray config, with the image `xray-ha` is pinned to in the Compose file (digest required), the config on stdin and no network.
4. Checks that `xray-ha` runs, keeps the files it is about to replace in `proxy-accounts/.apply-backup/`, and replaces them atomically: the configs, then the accounts file.
5. Restarts a fixed set of Compose services: `xray-ha`; with raw auth on, every running line; a line whose config changed; `blackbox-exporter` only if its config changed, which a request cannot cause.
6. Verifies through the HA entry's HTTP port, fetching the probe URL: `svc-monitor` and every newly added, enabled or rotated account must get 204, while every disabled or removed account, every replaced password and a wrong password must get 407. A running entry answers 407 whatever the lines do.
7. On a wrong answer, or no 407 within the timeout, it restores the files, restarts the same services and checks `svc-monitor` again (`failed`). When only the 204s are missing, the change stays (`unconfirmed`).

Then it writes the results, the statuses, `proxy-accounts/applied.json` and `status.json`. `applied.json` holds the hash of the accounts file at the applier's last apply; `status` compares it with the current file (`unapplied_changes`), which differs after a change with `proxy_accounts.py` until the next apply. If the applier is killed after the files were replaced, the next run restores them from the backup and marks the batch `failed` (`interrupted`). Passwords are never logged or written to a status: errors are scrubbed of every known password.

## Restart impact

Every change restarts the HA entry, and with raw auth on also every line. Established connections through them drop: downloads break and clients have to retry. Requests that start during the restart fail for a few seconds, as when `xray-ha` starts ([the HA entry](../../../docs/00_Network_Proxy.md#the-ha-entry)). A rollback restarts them once more, and a failed apply can keep the entry down for up to the verify timeout. Requests that arrive together are applied with one restart. A request that changes nothing (enabling an enabled account) restarts nothing.

While raw auth is off, disabling an account stops it only at the HA entry: the lines' own entries require no account, so it can still use them.

## Tests

```sh
cd services/proxy-portal/applier && python3 -B -m unittest discover -s tests -v
```

They cover request validation, the spool's handling of links, folders, foreign owners and oversized files, and the apply steps with injected failures: render, `xray -test`, restart, verification, rollback and an interrupted apply. Docker and the HA entry are simulated.
